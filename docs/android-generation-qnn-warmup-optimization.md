# Android Generation QNN Warmup Optimization

Status: implemented (Phase A warm reuse + Phase B forward-only graph).  Phase C
(context binary) not investigated.  All device numbers below are from the
NX741J / SM8850 physical device, QAIRT 2.48.40.260702151143, private D64/FFN64
step7500 checkpoint (hash `fnv1a64:3fc69abb8480b845`), Greedy, byte-BPE V1024.

## Baseline: where the ~20 s "Graph preparation" went

The cold path (`runNicopediaHtpGeneration`, FULL graph) reported, on the same
device/checkpoint (private report `seed1-l19-v1024-t32-d64-f64-greedy-step7500-max64-result.txt`):

| phase | time |
| --- | --- |
| htp_initialize (dlopen + backend/device/context create) | 2.91 s |
| graph_create | 0.074 s |
| graph_finalize | 2.70 s |
| generation loop (19 tokens, 62 bytes) | 2.25 s |

The UI's "Graph preparation" phase additionally contains the fixed-prefix
health gate (20 prefixes) and the 8-step autoregressive parity loop — 28 extra
executes, each ~118 ms, i.e. roughly 3.3 s of executes plus 19 CPU reference
forward passes — before the user's first generated byte.  The remaining wall
time is checkpoint decode + tokenizer load + prompt staging + process startup;
the total was dominated by per-Generate-press reconstruction of all of it.

## Phase A: process-local prepared generation engine

`qnn/qnn_prepared_generation.cpp` keeps one engine resident per process:

- prepare: checkpoint decode + HTP runtime init + FORWARD_ONLY graph
  finalize, once per cache key.
- run: identity re-validation (full checkpoint reload + parameter-hash
  compare, fail-closed), health gate, autoregressive loop on the resident
  graph.  No backend/device/context creation, no graph create/finalize.
- release: frees the engine; re-prepare after release rebuilds from scratch.
  Double release and use-after-release fail closed.

Cache key = checkpoint canonical path + file size + mtime + full header
identity (V/T/D/FFN/L/H/seed/step) + tokenizer kind/hash + parameter hash +
QAIRT build id + every graph option (precision mode/compensation/weights
packing/activation fusion/splitting/native FP16).  A different key or a
poisoned engine forces a fresh prepare.  Any QNN failure, non-finite tensor,
or identity mismatch poisons the engine; the next generation is a fresh
prepare.  There is no CPU fallback anywhere.

## Phase B: FORWARD_ONLY graph

`TinyTransformerTrainingVariant::FORWARD_ONLY` in the generalized N-layer/H-head
builder emits the shared forward chain (per-layer forward nodes plus the three
global nodes: embedding, position, logits).  It drops the target APP_WRITE,
the loss/softmax/dLogits chain, every gradient/backward tensor, and the
FULL-only STATIC tensors (`zero_ff`, `gradient_scale`).  Node counts, checked
fail-closed against the resource estimator's new `perLayerForwardNodes`:

- FULL (L19/H2): 2384 nodes, 2912 tensors
- FORWARD_ONLY (L19/H2): 953 nodes (= 19 × 50 + 3), 1877 tensors

The generation-only execute (`executeTinyTransformerForwardOnly`) binds
193 inputs (one-hot + 192 parameters) and reads 39 outputs (logits + 38
per-head probability taps kept for the established H>1 health ABI).  The FULL
execute is rejected on a FORWARD_ONLY graph and vice versa (fail-closed).

### 6004 root cause

The first device run of FORWARD_ONLY failed `graphExecute` with
`QNN_GRAPH_ERROR_INVALID_TENSOR (6004)`.  A bind manifest (metadata only:
registry id, name, type, rank, dims, element/byte counts, buffer non-null,
duplicate counts) emitted before the first execute showed the bind arrays were
consistent (193/39, zero duplicates, all buffers non-null, shapes correct).

The mismatch was inside the graph: the builder's `establishedOutput` rule
marks the last layer's `"output"` activation APP_READ whenever
`diagnosticOutputs` is true.  FULL's execute registry binds that tensor, but
FORWARD_ONLY's registry (correctly) skips it — leaving one APP_READ tensor in
the finalized graph that no execute ever bound.  Fix: `establishedOutput`
requires `!forwardOnly`, so the generation graph declares logits as its only
non-probability APP_READ.  FULL is byte-for-byte unchanged.

### Reading the numbers

- Graph create/finalize and HTP initialize are fully eliminated on warm runs
  (`graph_create_count_this_run=0`, `graph_finalize_count_this_run=0`,
  `htp_initialize_us=0`).  The Phase A acceptance criterion
  (same-checkpoint second generation: no rebuild, QNN success, finite,
  fallback=false, same checkpoint hash) is met on device.
- The dominant remaining per-run cost is the fixed-prefix health gate
  (~1.03 s of executes: 20 prefixes + 8 AR steps ≈ 28 executes × ~37 ms on
  the forward-only graph) plus checkpoint identity re-validation (full file
  reload + hash, ~0.08 s).  This is a deliberate, unchanged-semantics health
  cost, not a graph-preparation cost.
- Forward-only executes are faster than FULL executes (~37 ms vs ~118 ms per
  execute on this shape), which also shrinks the generation loop itself.
- First-byte latency for a warm same-checkpoint Generate is now bounded by
  the health gate, not by graph preparation.  Further reduction would require
  changing health-gate semantics (e.g. fewer prefixes), which was out of
  scope; the gate was not weakened.

## Health semantics

Unchanged: checkpoint identity (header/seed/step/registry/parameter hash) is
validated fail-closed on every prepare and every run; QNN return-code success
and application-visible finiteness are checked separately on every execute;
`cpu_fallback=false` is structural (no CPU path exists in the engine).  The
prepared report carries the same `qnn_return_code_success` /
`output_tensors_finite` / `generation_gate` / `generation_health` fields as
the cold report, plus `prepared_graph_reused`,
`graph_create_count_this_run=0`, and `graph_finalize_count_this_run=0`.  The
Kotlin parser cross-checks that a report claiming reuse really recorded zero
create/finalize counts.

## Caveats

- One prepared engine per process (max 1).  A different checkpoint key
  releases and rebuilds; there is no multi-engine eviction policy yet.
- The engine holds the resident graph but does not hold the
  `NativeRunArbiter` lock between runs; the arbiter is taken per execute as
  before.  Training and generation remain mutually exclusive.
- The bind manifest is emitted once per Runtime (first execute) into the
  private diagnostics; it contains metadata only, never tensor content.
- `prepared_graph_reused` reflects this run's relationship to the graph
  (run 1 on a fresh engine = false because that run's process paid prepare
  just before; run ≥ 2 = true).  `graph_*_count_this_run` is always 0 for
  prepared runs because prepare happens outside the run.
